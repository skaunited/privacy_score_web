## Configuration constatée

- Le module Apache `remoteip_module` est chargé.
- Le binaire Nginx du serveur inclut `--with-http_realip_module`.
- La configuration Apache Plesk utilise déjà `RemoteIPHeader X-Forwarded-For` avec le proxy interne `127.0.0.1`.
- Nginx transmet `X-Real-IP $remote_addr` et `X-Forwarded-For $proxy_add_x_forwarded_for` vers Apache.
- La configuration Nginx effective ne contient actuellement aucun `real_ip_header`, `set_real_ip_from` ou `real_ip_recursive`.
- Les champs Additional Apache directives du domaine sont vides. Les directives Nginx additionnelles sont celles générées par le dépôt ; elles ne nécessitent pas de remplacement pour cette correction.
- Aucune plage Cloudflare n’est actuellement dans la liste d’exclusion Fail2Ban consultée.

La chaîne actuelle journalise donc le relais Cloudflare comme visiteur. Une détection GPTBot peut bannir un relais utilisé ensuite par des visiteurs ordinaires ou d’autres robots. Cela correspond à la [cause d’erreur 521 décrite par Cloudflare](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-521/).

## Correction préparée, à approuver avant application

La proposition a une **portée serveur**, car la jail surveille tous les domaines. Une correction limitée au vhost Privacy Score laisserait les autres domaines capables de faire bannir les mêmes relais pour toute la VM.

1. Installer [`deploy/cloudflare-realip.nginx.conf`](../deploy/cloudflare-realip.nginx.conf) dans le contexte HTTP global de Nginx (`/etc/nginx/conf.d/cloudflare-realip.conf`), après sauvegarde et vérification de l’absence de configuration concurrente. Il contient exclusivement les 15 plages IPv4 et 7 plages IPv6 des listes officielles consultées, `real_ip_header CF-Connecting-IP` et `real_ip_recursive on`. Les connexions directes hors Cloudflare ne deviennent pas des proxys de confiance. Tester `nginx -t` avant tout rechargement ; retirer/restaurer le nouveau fichier si la validation échoue. Recharger Nginx sans redémarrage complet.
2. Retirer uniquement le token exact `GPTBot` du paramètre `badbots` via `/etc/fail2ban/filter.d/apache-badbots.local`, en conservant tous les autres tokens et les éventuelles options locales existantes. Sauvegarder le fichier local s’il existe. Construire la valeur depuis le filtre effectif constaté et refuser l’opération si le token n’est pas présent exactement une fois. Tester que les User-Agents GPTBot simples et officiels ne déclenchent plus la jail, et que Bytespider reste détecté. Valider `fail2ban-client -t` avant de recharger cette jail. Cette surcharge conserve une copie de la liste des autres bots : elle devra être revue lors d’une mise à jour du filtre fourni par le paquet.
3. Débannir uniquement les quatre IP listées ci-dessus dans `plesk-apache-badbot`, après vérification de leurs bannissements courants. Ne pas vider les autres jails, y compris `recidive`, et ne pas ajouter toutes les plages Cloudflare à une liste de confiance globale Fail2Ban.

Fail2Ban, ModSecurity, le pare-feu et le WAF Cloudflare restent actifs. La suppression de GPTBot de cette classification ne valide pas son identité : les autres règles de sécurité doivent continuer à traiter ses requêtes. La restitution d’IP permet de journaliser le visiteur ; elle ne suffit pas à bloquer un visiteur proxifié avec une simple action iptables sur son IP, puisque le TCP arrive toujours de Cloudflare. Les protections HTTP et celles du proxy restent nécessaires.

La procédure n’envoie ni build ni fichiers du site vers Plesk et ne modifie pas les branches Git distantes. Le nouveau snippet global ne doit pas être collé dans le champ Additional nginx directives du domaine ni copié dans le document root public.

Références : [Plesk : restituer l’IP derrière Cloudflare](https://support.plesk.com/hc/en-us/articles/12377061126807-Incorrect-IP-addresses-are-logged-by-Plesk-behind-a-Cloudflare-or-Google-Cloud-Load-Balancing), [Cloudflare : restituer les IP et déclarer les proxys de confiance](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/), [Plesk : diagnostic des bannissements](https://support.plesk.com/hc/en-us/articles/12377059413911-How-to-check-why-an-IP-address-is-getting-banned-by-Fail2Ban-in-Plesk-for-Linux).

## Vérifications après application et retour arrière

La proposition a déjà été vérifiée localement contre les deux listes Cloudflare publiques : 22 CIDR exacts, aucun doublon, aucune plage de confiance universelle, les quatre relais bannis appartiennent aux plages attendues. Un Nginx 1.30.6 isolé, compilé avec le module realip, accepte sa syntaxe. Huit requêtes HTTP locales ont vérifié que les faux en-têtes IPv4/IPv6 d’une source non approuvée sont ignorés, que le contrôle simulant un proxy approuvé restitue bien l’IPv4/IPv6 transmise, et que `X-Forwarded-For` seul ne suffit pas à imposer une adresse. Ces tests ne remplacent pas `nginx -t` et les contrôles sur la VM avant/après rechargement.

- Lire de nouvelles entrées Nginx et Apache d’une requête contrôlée : elles doivent porter l’IP publique du client de test, plutôt qu’une IP Cloudflare. Ne pas publier cette adresse dans le dépôt.
- Contrôler qu’une connexion directe à l’origine avec un faux en-tête `CF-Connecting-IP` ne permet pas d’usurper une IP de confiance ; ne pas assouplir le pare-feu pour effectuer ce test.
- Vérifier l’accueil EN/FR, les deux index et les huit articles avec un client normal et les robots concernés, à faible concurrence. Conserver tous les échecs initiaux dans le rapport, même si un contrôle ultérieur réussit.
- Vérifier que les quatre relais sont débannis, qu’aucun nouveau relais Cloudflare n’est banni pendant ces contrôles et que les services restent actifs. L’absence d’erreur sur cet échantillon ne garantit pas la disponibilité future.
- Retour arrière : restaurer le fichier `.local` sauvegardé (ou retirer uniquement celui créé), valider et recharger la jail ; restaurer/retirer uniquement le fichier Nginx ajouté, valider puis recharger Nginx. Les bans levés ne doivent pas être recréés automatiquement ; réévaluer leur nécessité avec les journaux. Conserver les sauvegardes hors document root.

**État : proposition préparée, non appliquée.** La confirmation au moment de l’action est requise par la politique de navigation, car cette opération modifie des proxys de confiance et lève des blocages réseau. Aucune désactivation générale des protections n’est proposée.
